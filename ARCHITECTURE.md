# Архитектура Primelab Knowledge Agent

Проект MVP на 24 ноября. Стек по умолчанию — Python 3.11+, SQLite FTS5, Ollama и FastAPI с одной серверной HTML-страницей. Для текстовых PDF — pypdf, для DOCX — python-docx, для TXT/Markdown — стандартная библиотека. Установить только парсеры форматов, реально полученных по ТЗ. PDF-сканы и дополнительные форматы оценить по доле в корпусе и обязательности. При обязательных сканах выделить время на локальный OCR с проверкой таблиц и страниц.

## Загрузка и индекс

1. Оператор импортирует выданный каталог локально. Сохраняются неизменённые оригиналы, контрольные суммы, стабильные идентификаторы и отчёт об ошибках извлечения. Для PDF адресом доказательства служит страница и пункт, для DOCX — заголовок и нумерованный абзац или строка таблицы. Страницы DOCX указываются только при наличии надёжной привязки.
2. Извлечение сохраняет структуру пунктов, заголовки и связи заголовков таблиц с ячейками. Сложные таблицы и нечитаемые страницы попадают в отчёт. Фрагменты формируются по подразделам, с сохранением номера пункта и небольшим перекрытием только на границах длинного блока.
3. Реестр корпуса хранит семейство, ID редакции, SHA-256, название, область применения, даты начала и окончания действия, отношения замены, исходный источник и основание каждого атрибута. Метаданные организатора и явно указанные нормы сверяются с текстом. Неоднозначные даты хранятся как неизвестные до проверки. Индексация идемпотентна по хешу и версии правил извлечения. Новый индекс заменяет предыдущий после успешной проверки, ошибки импорта видны оператору.
4. Сначала поднимается поиск FTS5/BM25 по заголовкам, пунктам, именам и содержимому. Контрольные запросы с русскими словоформами и перефразированием сравниваются на том же корпусе. При нехватке полноты и работоспособном локальном `bge-m3` добавляется объединение рангов лексического и векторного поиска. Для небольшого корпуса достаточно локальных векторов и точного косинусного поиска. Переоценить размер индекса после инвентаризации. [Документация SQLite FTS5](https://www.sqlite.org/fts5.html) · [Ollama Embed](https://docs.ollama.com/api/embed)

## Обработка вопроса

1. Определить дату среза (по умолчанию текущая дата в МСК), выделить явные номера документов и пункты. При запросе исторической нормы использовать срез пользователя. Если смысл существенно зависит от подразделения, юрисдикции или значения даты, уточнить недостающий параметр.
2. Искать по всем допущенным к этому стенду документам. Для составного вопроса получить отдельные результаты по его частям, ограничить число фрагментов одного документа, выполнить один дополнительный поиск по явным отсылкам или части вопроса без доказательств. Сохранить представительство обязательных регламентов в пакете доказательств. По каждому существенному выводу должна остаться привязка к релевантному источнику.
3. Сопоставить редакции одного семейства для даты и области запроса. Явно отменённые, будущие и просроченные редакции можно показать как контекст сравнения с маркировкой. Для текущего вывода используется применимая подтверждённая редакция. Дата загрузки, дата файла и более поздняя дата публикации сами по себе приоритет не задают. При разных документах сначала сверить применимость и официальное правило приоритета. Если обе нормы применимы и расходятся, показать обе с датами, цитатами и открытым вопросом, который должен решить владелец процесса.
4. Передать в Ollama только вопрос и ограниченный набор фрагментов. Пусковой кандидат — `gemma3:4b`, запасной по качеству на GPU — `gemma4:e4b` после проверки. Генерировать структурированный ответ со статусом, короткими утверждениями, идентификаторами доказательств и выдержками. На начальной конфигурации — один проход генерации с низкой температурой и ограничением выхода. [Ollama Generate](https://docs.ollama.com/api/generate)
5. Проверить схему, статус применимости, существование ID и соответствие цитаты исходному фрагменту. Ссылки формировать из реестра. Для дат, чисел и единиц выполнять сверку с процитированным текстом, где формат позволяет. Валидатор привязки сам по себе не доказывает смысловое следование, поэтому его дополняет ручная приёмка. При отсутствии доказательств, тайм-ауте или ошибке схемы панель показывает статус и найденные выдержки, если они доступны и допустимы. Частичный ответ явно отмечает неподтверждённую часть.

## Демонстрационная панель и данные

- Вопрос, поле даты среза, ответ и статус, раскрываемые источники с версией и локатором. Примерные вопросы отобрать только после изучения корпуса. Загрузка корпуса остаётся отдельной операторской операцией.
- Ollama привязана к loopback. Приложение не передаёт тексты, векторы, промпты или вопросы внешним LLM и облачным инструментам. Локальная проверка внешних соединений проводится на синтетике, затем тест повторяется на разрешённом корпусе.
- Загружаемые документы и вопрос считаются данными. Инструкции из них игнорируются. Модели недоступны оболочка, сеть, произвольные пути и операции записи. UI экранирует фрагменты и использует идентификаторы из реестра. Логи содержат статусы, длительность и счётчики без текстов и локальных путей.
- На стенд выносится только отдельно допущенный корпус. Доступ жюри, ограничения на выдачу фрагментов, срок доступности и права на показ сверяются с ТЗ. На внешнем входе — HTTPS, предусмотренный организатором доступ, лимит входа, тайм-аут, ограниченная очередь. Доступ к необработанным файлам и внутреннему API закрывается.

Для MVP достаточно одного процесса приложения, одного индекса и последовательной обработки запросов. Поток поиска, уточнения, сверки редакций и генерации сам выполняет необходимые действия в этих границах. SSO, административный интерфейс, отдельная векторная БД и масштабирование откладываются до явного требования.
