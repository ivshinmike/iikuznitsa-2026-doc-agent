## Подготовка Git

1. Использовать отдельный приватный репозиторий с веткой `main`. Подготовительные материалы фиксируются отдельным коммитом до старта. Конкурсные коммиты начинаются 26 ноября в 10:00 МСК. Указать фактическое время старта и делать небольшие коммиты по функциям.
2. Отслеживать по явному списку исходники, тесты и синтетические фикстуры, инструкции по запуску, зависимости, публично допустимые проектные описания, лицензии и сведения о моделях. Указать фиксированные версии и идентификаторы. Публичную инструкцию проверить из чистой копии на синтетике. Проверить право на публикацию сторонних компонентов, текстов и тестовых примеров.
3. Сверить `.gitignore` с фактическими путями через `git check-ignore`. Из проверки исключений отдельно подтвердить разрешённую фикстуру. Перед каждым существенным коммитом проверять список индексируемых файлов и staged diff. Рабочие данные и производные индексы, организаторские документы, журналы, ключи, веса моделей, расчёты и видео держать в отведённых локальных каталогах. В `.env.example` оставлять только пустые значения и заглушки.
4. Перед открытием проверить также всё, что попадёт в историю, включая удалённые в поздних коммитах файлы, ветки, теги и Git LFS при наличии. Просмотреть имена путей, содержимое коммитов, крупные объекты и результаты локального поиска секретов. Если выявлен секрет, остановить публикацию, организовать отзыв через владельца и проверить очищенную историю. При отсутствии сканера выполнить ручной обзор и явно указать охват.
5. После отдельного разрешения владельца выполнить процедуру ниже. Открыть только согласованные ссылки на остальные материалы и проверить, что стенд соответствует контрольному SHA.

## Перевод GitHub в Public

1. Зафиксировать SHA кандидата и сверить GitHub refs с локальными после `git fetch --prune --tags origin`. Проверить содержимое всех публикуемых веток и тегов, полную историю, LFS, релизы, вложения, открытые обсуждения, Actions и их журналы. Проверить права на распространение кода, моделей и примеров. Отдельно проверить сведения об инфраструктуре, персональные данные и метаданные коммитов.
2. Записать объём проверки и результаты. Если есть чувствительные сведения, сначала устранить их во всех видимых копиях, проверить историю заново и передать владельцу проверенный SHA. До его отдельного разрешения видимость — **Private**.
3. В согласованное время владелец или уполномоченный исполнитель открывает **Settings → Danger Zone → Change repository visibility → Public**, сверяет имя `ivshinmike/iikuznitsa-2026-doc-agent` и подтверждает действие. GitHub открывает историю Actions и журналы, разрешает форки и может изменить применяемые правила push. [GitHub Docs](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/managing-repository-settings/setting-repository-visibility)
4. Из сессии без GitHub-авторизации проверить страницу, ветку `main`, её историю и чистое клонирование. Сопоставить HEAD с утверждённым SHA, повторить запуск по опубликованной инструкции и сохранить подтверждение доступа.

## Стоимость одного запроса

1. Получить официальный шаблон и сохранить исходную версию. Сопоставить поля с замерами релизного стенда. До получения шаблона числа и ставки остаются открытыми.
2. Зафиксировать профиль запроса, модель, железо, контекст, тёплый и холодный режимы, число измерений, токены входа и выхода, p50/p95 полного времени и долю ошибок. Отдельно собрать данные индексации: объём, периодичность, время, хранение.
3. Для ПК собрать подтверждённый тариф на электроэнергию, замер или явно отмеченную оценку мощности всей системы и допущения об амортизации. Для VPS взять фактическую стоимость используемого периода из биллинга и выделенную долю ресурса. Показать базовый и низкий объёмы нагрузки, валюту и дату ставки. Нулевая ставка внешних токенов при локальном вычислении учитывается отдельно от инфраструктуры.
4. Для модели с фиксированными расходами за период рассчитать их долю на число успешных запросов за тот же период, добавить переменные расходы и распределённую стоимость обновления корпуса. Для поминутной ставки использовать занятое время и стоимость единицы времени. Одну статью расхода учитывать один раз. Указать допущения о простое, повторных попытках и параллельности. Перенести значения и формулы в поля организатора.
5. Пересчитать на контрольной строке вручную и сверить единицы. Провести ревизию ссылок и скачивания после разрешения владельца.
